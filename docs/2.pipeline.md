

Model and Decision Logic

The model calculates the complete end-to-end cost of JSON, JSON + GZIP, and MessagePack
under a given workload and network condition. The decision model then uses these calculated
costs and the measured trade-offs to select the most suitable format. The objective is not to
prove that MessagePack is always better, but to determine when its network savings justify its
computational overhead.

## 1. Model Inputs

For every experimental configuration, the model uses:

S = payload size

D = data structure

R = redundancy / compressibility

B = network bandwidth

L = network latency

C = computational resources

Format = JSON / JSON + GZIP / MessagePack


These variables define the conditions under which the format is evaluated.

Additional measured inputs include:

Serialization time

Compression time

Deserialization time

Decompression time

CPU usage

Memory usage

## Energy


Network transmission time

Payload size

Debugging importance



## ---

- Total End-to-End Cost Model

For every format f:

## T_f = T_ser,f + T_comp,f + T_net,f + T_decomp,f + T_deser,f

where:

T_ser = serialization time

T_comp = compression time

T_net = network transmission time

T_decomp = decompression time

T_deser = deserialization time


Stages that do not apply to a format are set to zero.

## JSON

T_JSON = T_ser,J + T_net,J + T_deser,J

## JSON + GZIP

T_GZIP = T_ser,J + T_comp,G + T_net,G + T_decomp,G + T_deser,J

MessagePack

T_MP = T_ser,MP + T_net,MP + T_deser,MP



## ---

## 3. Network Cost Model

The basic network model is:

## T_net = L + S / B

where:

L = network latency

S = transmitted payload size in bits

B = effective bandwidth in bits per second


Therefore, reducing payload size becomes increasingly important as bandwidth decreases.

For each format:

T_net,J = L + S_J / B

T_net,G = L + S_G / B

T_net,MP = L + S_MP / B

where:

S_J = JSON payload size

S_G = GZIP payload size

S_MP = MessagePack payload size


The experimental model should also record actual transmission time because real networks
include packet, protocol, connection, and other overheads. These effects should be measured
rather than hidden inside the simplified equation.


## ---


## 4. Payload Reduction Model

JSON is used as the baseline.

For any alternative format f:

Payload Reduction_f = 1 - S_f / S_J

For JSON + GZIP:

Payload Reduction_G = 1 - S_G / S_J

For MessagePack:

Payload Reduction_MP = 1 - S_MP / S_J

This determines how much data is removed from the network transmission compared with
normal JSON.


## ---

## 5. Compression Model

For JSON + GZIP:

Compression Ratio = S_G / S_J

Compression Saving = S_J - S_G

Compression Saving Percentage = (S_J - S_G) / S_J

The model must consider both the network benefit and the computational cost of obtaining that
smaller payload.

## Therefore:

GZIP Benefit = Network Time Saved

GZIP Cost = Compression Time + Decompression Time


## ---


## 6. Computational Cost Model

Computational overhead is the additional processing required by a format compared with the
baseline.

For MessagePack:

O_MP = (T_ser,MP + T_deser,MP) - (T_ser,J + T_deser,J)

For JSON + GZIP:

O_G = T_comp,G + T_decomp,G

The model also records CPU and memory overhead separately.

The central trade-off is:

Network Saving vs Computational Overhead

This allows the study to determine whether a smaller payload actually produces a lower total
latency.


## ---

## 7. Network Saving

Network time saved by format f compared with JSON:

N_f = T_net,J - T_net,f

## If:

## N_f > 0

the format saves network time.

## If:

## N_f = 0

there is no network-time advantage.

## If:


## N_f < 0

the alternative requires more network time.


## ---

## 8. Computational Overhead

Additional processing time compared with JSON:

O_f = ProcessingTime_f - ProcessingTime_JSON

For MessagePack:

O_MP = (T_ser,MP + T_deser,MP) - (T_ser,J + T_deser,J)

For GZIP:

O_G = T_comp,G + T_decomp,G

A format is attractive when its network saving is greater than its additional computational cost.


## ---

## 9. Net Performance Benefit

For every alternative format:

Benefit_f = T_JSON - T_f

## If:

## Benefit_f > 0

the alternative is faster than JSON.

## If:

## Benefit_f = 0

both formats have equal end-to-end performance.


## If:

## Benefit_f < 0

JSON is faster.

The same calculation can be performed between GZIP and MessagePack.

For MessagePack compared with GZIP:

Benefit_G_to_MP = T_GZIP - T_MP

The source model explicitly defines the JSON-to-MessagePack comparison using this
difference.


## ---

## 10. Relative Gain

Relative gain measures the percentage improvement compared with JSON.

Relative Gain_f = (T_JSON - T_f) / T_JSON

Percentage form:

Relative Gain Percentage_f = Relative Gain_f x 100

## Example:

T_JSON = 100 ms

T_MP = 70 ms

Relative Gain_MP = (100 - 70) / 100 = 0.30

## Therefore:

Relative Gain_MP = 30%

The relative gain is used for the practical switching decision.



## ---

- Payload Break-Even Point

The first major break-even point is the payload-size threshold.

The question is:

At what payload size does an alternative format become sufficiently beneficial compared with
the current format?

For JSON versus MessagePack:

## T_JSON = T_MP

At the theoretical break-even point:

T_ser,J + T_net,J + T_deser,J

## =

T_ser,MP + T_net,MP + T_deser,MP

## Using:

## T_net = L + S / B

and assuming the same network latency:

T_ser,J + T_deser,J + L + S_J/B

## =

T_ser,MP + T_deser,MP + L + S_MP/B

The latency terms cancel:

T_ser,J + T_deser,J + S_J/B

## =

T_ser,MP + T_deser,MP + S_MP/B

The experiment then evaluates this relationship across increasing payload sizes.


The resulting payload value is the theoretical crossover size where the two formats have equal
end-to-end cost.


## ---

- Practical Payload Break-Even

The theoretical crossover is not automatically the practical switching point.

The study defines:

Relative Gain = (T_baseline - T_alternative) / T_baseline

Then evaluates whether the improvement crosses the selected engineering threshold.

The original design identifies:

Relative Gain = 0% -> theoretical equality

Below 10% -> negligible improvement

20% or more -> practical break-even

50% or more -> strong advantage


These values should be treated as methodology thresholds and justified or sensitivity-tested
rather than presented as universal constants.

The payload break-even result therefore becomes:

Payload_BE = minimum payload size where Relative Gain >= threshold

This is calculated separately for:

## JSON -> JSON + GZIP

JSON -> MessagePack

JSON + GZIP -> MessagePack



The final results identify the size threshold where compression becomes useful and the size
threshold where binary serialization becomes useful.


## ---

- Network Break-Even Point

The second major break-even point is bandwidth.

The question is:

At what bandwidth does the smaller payload of an alternative format compensate for its
additional processing cost?

For JSON versus MessagePack:

## T_JSON = T_MP

Using the end-to-end model:

T_ser,J + T_deser,J + L + S_J/B

## =

T_ser,MP + T_deser,MP + L + S_MP/B

## Cancel L:

T_ser,J + T_deser,J + S_J/B

## =

T_ser,MP + T_deser,MP + S_MP/B

## Rearranging:

## (S_J - S_MP) / B

## =

(T_ser,MP + T_deser,MP) - (T_ser,J + T_deser,J)

## Therefore:


## B_BE,JSON-MP =

(S_J - S_MP) / [(T_ser,MP + T_deser,MP) - (T_ser,J + T_deser,J)]

This is the analytical break-even bandwidth under the simplified network model.

## Interpretation:

B < B_BE -> MessagePack has enough network saving to compensate for its additional
processing cost.

B > B_BE -> MessagePack's smaller payload may not compensate for its additional processing
cost.

B = B_BE -> both have equal predicted end-to-end cost.


The actual paper should calculate this from measured serialization and deserialization times
and measured payload sizes rather than using assumed values. The source specifically
identifies this bandwidth boundary as a central mathematical result.


## ---

- JSON + GZIP Network Break-Even

The same calculation is applied to JSON + GZIP.

At break-even:

## T_JSON = T_GZIP

## Therefore:

T_ser,J + T_net,J + T_deser,J

## =

T_ser,J + T_comp,G + T_net,G + T_decomp,G + T_deser,J

The common JSON serialization and deserialization terms cancel:

T_net,J


## =

T_comp,G + T_net,G + T_decomp,G

Using the simplified network model:

## L + S_J/B

## =

T_comp,G + L + S_G/B + T_decomp,G

## Therefore:

## (S_J - S_G) / B

## =

T_comp,G + T_decomp,G

## So:

## B_BE,JSON-GZIP =

(S_J - S_G) / (T_comp,G + T_decomp,G)

## Interpretation:

Below this bandwidth, GZIP's smaller payload has greater opportunity to compensate for
compression overhead.

Above this bandwidth, the compression/decompression cost may dominate.

The actual result must be obtained using measured values.



## ---

- GZIP vs MessagePack Break-Even

The same approach is used to determine the crossover between the two optimized alternatives.


At break-even:

## T_GZIP = T_MP

## Therefore:

T_ser,J + T_comp,G + T_net,G + T_decomp,G + T_deser,J

## =

T_ser,MP + T_net,MP + T_deser,MP

Using the network model:

T_ser,J + T_comp,G + T_decomp,G + S_G/B

## =

T_ser,MP + T_deser,MP + S_MP/B

## Rearranging:

## B_BE,GZIP-MP =

(S_G - S_MP) / [(T_ser,MP + T_deser,MP) - (T_ser,J + T_comp,G + T_decomp,G + T_deser,J)]

This provides the third pairwise boundary when sufficient experimental data is available.

The source explicitly identifies JSON-GZIP, JSON-MessagePack, and potentially
GZIP-MessagePack as the relevant boundaries.


## ---

- Latency and Bandwidth Interaction

Network latency affects all formats, while payload size affects the transmission component.

Under the simplified model:

T_net = L + S/B

## Therefore:


High latency increases total latency for all formats.

Low bandwidth increases the importance of payload reduction.

Large payloads increase transmission time.

Smaller payload formats gain more advantage as bandwidth decreases.


The model therefore does not treat payload size independently from network conditions.


## ---

- CPU Constraint Trade-Off

CPU capability is introduced as an additional constraint.

Two systems can be compared:

Powerful CPU

Resource-constrained CPU


A format that performs well on a powerful server may perform differently on a
resource-constrained system because serialization, compression, decompression, and
deserialization consume different amounts of CPU resources.

The model therefore evaluates:

CPU Cost vs Network Saving

For every format:

Additional CPU Cost = CPU Cost_format - CPU Cost_JSON

Network Saving = Network Time_JSON - Network Time_format

The main trade-off plot uses:

X-axis = Additional CPU Cost

## Y-axis = Network Time Saved


This directly shows whether network savings justify computational overhead.


## ---

- Energy Trade-Off

If energy measurement is included:

Energy = CPU Time x CPU Power + Data x Network Power

For each format:

E_f = E_CPU,f + E_Network,f

The comparison is:

Energy Saving_f = E_JSON - E_f

A format may therefore have lower latency but higher energy consumption, or lower network
usage but higher CPU energy.

Energy is kept as a separate dimension rather than being mixed directly into milliseconds.


## ---

- Adoption and Engineering Cost

Performance alone does not determine whether a format should be adopted.

The switching cost is represented as:

## C_switch = C_implementation + C_maintenance + C_complexity

Engineering factors include:

## Readability

Debugging difficulty

Tooling effort



These costs should not be artificially converted into milliseconds. Instead, they remain a
separate practical decision dimension.

## Therefore:

## Performance Winner != Practical Recommendation

The fastest format may not be the recommended format if its improvement is small and its
adoption cost is substantially higher.


## ---

- Practical Worth-It Condition

A format is considered worth switching to when:

- It provides a meaningful end-to-end improvement.


- Its computational overhead is acceptable.


- Its network savings are significant under the given network condition.


- Its adoption/engineering cost is acceptable.



## Conceptually:

Worth Switching = Performance Benefit + Acceptable Computational Cost + Acceptable
## Adoption Cost

The model keeps performance benefit and adoption cost as separate dimensions rather than
combining incompatible units into one arbitrary number.


## ---

- Three-Zone Decision Model


The practical decision is divided into three zones.

## Zone 1 - No Switch

R_best < tau_low

Example sensitivity value:

## R < 5%

## Meaning:

Improvement is too small.

Stay with the current format.

Switching cost is unlikely to be justified.


## Zone 2 - Evaluate

tau_low <= R_best < tau_high

## Example:

## 5% <= R < 20%

## Meaning:

A measurable improvement exists.

Compare CPU, memory, energy, debugging, and implementation cost.

GZIP may be preferred over MessagePack if it provides a similar performance benefit with lower
adoption cost.


## Zone 3 - Switch

R_best >= tau_high

## Example:

## R >= 20%


## Meaning:

Performance improvement is substantial.

The alternative should be seriously considered.

Final selection still considers computational and engineering constraints.


The 5% and 20% values are example thresholds and must be justified or tested through
sensitivity analysis in the final study.


## ---

## 22. Performance Winner

For every experimental condition:

T_best = min(T_JSON, T_GZIP, T_MP)

## Therefore:

Best Performance Format = argmin(T_JSON, T_GZIP, T_MP)

This identifies the format with the lowest measured end-to-end latency.

However, this is only the performance winner.

The final decision also evaluates whether the improvement is large enough to justify switching.


## ---

## 23. Decision Score

The final decision framework can use a weighted score:

## Score_f =

Wn x NetworkGain_f

Wc x CPUCost_f


Wm x MemoryCost_f

We x EnergyCost_f

Wd x DebugCost_f


where:

Wn = importance of network performance

Wc = importance of CPU cost

Wm = importance of memory cost

We = importance of energy

Wd = importance of debugging/engineering cost


The format with the highest score is selected by the decision layer.

The weights are application-dependent and should be explicitly reported rather than hidden.


## ---

## 24. Decision Logic

The implemented decision process is:

- Identify the workload.


- Identify payload size.


- Identify redundancy.


- Identify bandwidth.



- Identify network latency.


- Identify CPU and memory constraints.


- Measure or estimate the required format-specific costs.


- Calculate T_JSON.


- Calculate T_GZIP.


- Calculate T_MP.


## 11. Determine T_best.


- Calculate relative gain.


- Check the practical gain threshold.


- Calculate payload break-even condition.


- Calculate network break-even condition.


- Evaluate CPU and memory constraints.


- Evaluate energy if enabled.


- Evaluate engineering/debugging importance.


- Calculate the decision score.



- Select the practical recommendation.


- Report confidence and reason.



This separates the cost model from the decision model: the cost model calculates performance,
while the decision model selects the appropriate format.


## ---

- Rule-Based Layer

A rule-based layer is applied before the final recommendation.

Initial rules from the proposed framework are:

Small payload -> JSON

Medium payload -> JSON + GZIP

Large payload -> MessagePack

High CPU constraint -> avoid computationally expensive alternatives

Debugging critical -> prefer JSON


These are not fixed conclusions. They are starting rules that the experimental results and
break-even analysis must validate or modify.


## ---

## 26. Final Recommendation Logic

The final recommendation distinguishes three outputs:

## Performance Winner:

Format with minimum end-to-end latency.



## Practical Recommendation:

Format that provides sufficient improvement while satisfying CPU, memory, energy, and
engineering constraints.


## Confidence:

Based on the measured relative gain and stability of the result.


## Reason:

## Network-bound

CPU-bound

## Memory-bound

## Compression-beneficial

## Binary-beneficial

Engineering/debugging constrained



## ---

## 27. Model Validation

The decision framework must be tested using previously unseen experimental configurations.

## Example:

Payload size = new value

Bandwidth = new value

Redundancy = new value

CPU condition = new value



The model first predicts the recommended format.

The same configuration is then actually executed.

## Prediction Accuracy = Correct Predictions / Total Validation Cases

If the predicted format wins experimentally, the framework is supported for that condition.

If it does not, the model parameters or decision boundaries must be refined.

This validation step is specifically intended to demonstrate that the framework has predictive
value rather than simply describing the benchmark results.
